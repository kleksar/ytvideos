# ChatGPT browser session

Use this skill for ChatGPT.com work in Google Chrome, including required project consultations, model selection, reasoning effort, and tab cleanup. This procedure is the single owner for browser session handling. Project-specific requirements for research, editorial scope, records, and required consultation stages remain with the relevant root or topic skill.

## Prepare the session

1. Read the project root instructions, bootstrap, and the applicable task-specific skill. Resolve the exact task and its allowed inputs before opening ChatGPT.
2. Before opening or focusing a ChatGPT tab, acquire the shared composer lock described below. If it is busy, do not open another ChatGPT tab or edit a composer; do independent work and resume when the lock is free.
3. Use a visible Chrome tab. Prefer reusing an agent-created tab already dedicated to the same task. Do not duplicate a live user session or create multiple tabs for the same task without a concrete need.
4. Inspect the visible conversation and composer under the lock before interacting.

## Coordinate the shared composer

An unsent draft may appear across tabs in this profile. This is an observed coordination precaution, not a universal browser guarantee. The lock is advisory: it coordinates cooperating local clients only, not users, other machines, older running clients or in-flight browser actions. Use the same shared lock; do not interrupt active sessions. A PID, timeout, hash or free lock alone never proves ownership or safety to clear.

Use `python3 .agents/skills/ytv-chatgpt-session/scripts/composer_recovery.py --task-id UNIQUE_TASK_ID --wait` with stdin kept open. The helper accepts one JSON object per line and returns one JSON object per line. All browser observations below are the caller's attestations, not checks made by the helper. Keep the lock only while identifying, editing, submitting and verifying the shared composer; release on confirmed send and wait for the response outside the lock.

1. Save the exact UTF-8 prompt in the task record before input. After acquiring the lock, inspect the specific original tab, conversation and composer. Record a stable tab/chat identifier and a visible history anchor: last visible outgoing message or explicitly documented empty conversation. Do not enter over any nonempty or unknown draft. Record model and mode before sending.
2. Before the first character, send `{"op":"prepare","prompt_file":"/absolute/path/to/exact-prompt.txt","chat":"CHAT_AND_TAB_ID","history_anchor":"VISIBLE_ANCHOR","initial_empty":true}`. Wait for `PREPARED`. The durable journal contains the exact text, owner, original chat/tab and anchor; it is local and private. Use a supported input method that does not modify the shared clipboard; do not use multiline `typeText` if it can submit on newline. Any input can accidentally submit: immediately inspect the entire original conversation since the anchor and the composer before proceeding.
3. Only after the entire visible composer exactly equals the saved prompt in the original chat, send `{"op":"inserted","chat":"CHAT_AND_TAB_ID","observed_text":"EXACT FULL PROMPT"}`. Before the visible Send control, inspect all outgoing messages since the anchor and compare the field again. Only if no unexpected submission occurred, send `{"op":"send_attempt","chat":"CHAT_AND_TAB_ID","observed_text":"EXACT FULL PROMPT","history":"none"}` and wait for `SEND_ATTEMPT_RECORDED`. Click Send once. Verify the exact posted message and empty field, then send `{"op":"confirmed","chat":"CHAT_AND_TAB_ID","posted_text":"EXACT FULL PROMPT","composer_empty":true}`. The helper releases immediately. Its JSON inputs carry exact strings with proper JSON escaping; do not use hashes as a substitute for comparison.
4. An interruption after `PREPARED` leaves a durable unresolved operation even if no send was planned. On `NEEDS_INSPECTION`, keep the lock and inspect the original chat since the anchor and its composer. A completed prompt, any partial outgoing message, or ambiguous history must never be blindly resent. Record actual outgoing content and the decision in the original task record. For a partial submission, evaluate the conversation and decide a fresh continuation or correction; do not send the full prompt automatically. If history or identity cannot be established, leave the field untouched and release without resolving.
5. To reconcile, send `{"op":"reconcile","chat":"CHAT_AND_TAB_ID","history":"none|full|partial|unknown","observed_text":"EXACT VISIBLE FIELD","no_intervening_edit":true}` with one actual history value, only after the corresponding observations. A field empty on inspection additionally requires `"composer_empty":true`. `EXACT_AGENT_DRAFT` permits clearing only an entire exact, previously observed inserted prompt, with the same chat, preserved source and no evidence of user intervention. Immediately before clearing, recheck exact visible field and identity; stop on any discrepancy. Clear using supported UI, verify the field is empty, record the outcome, and send `{"op":"cleared","chat":"CHAT_AND_TAB_ID","composer_empty":true}`. The system cannot atomically compare and clear: if a human or non-cooperating client may edit concurrently, do not clear. Partial, modified, mixed, unknown or personal text is never automatically classified from a prefix/hash or cleared. If the crash occurred before `inserted`, even an apparent match remains unverified: inspect and stop.
6. For `STOP`, preserve the evidence and leave the draft untouched. If there is a matching legacy unresolved marker, follow the old original-chat inspection protocol; never assert `INSPECTED` without resolving the evidence. An older process already holding the previous script cannot be forced to follow the new protocol. After a crash during clearing, repeat full chat, ownership and exact-field checks; never assume the clear completed.

A `partial` or `full` recovered history outcome records a durable hold keyed by the exact full prompt hash before resolving or clearing. It survives unrelated new operations and prevents preparing that same prompt in any chat; `SUBMISSION_HOLD` identifies the original operation without sending. The last resolved v2 recovery with `partial` or `full` history is migrated on the next new-helper acquisition; older overwritten history cannot be reconstructed from this journal. This intentionally favors safety over progress if identical text is legitimately needed elsewhere. A corrected prompt is a separate decision; never use a trivial edit to bypass a duplicate. Only after inspecting the original conversation and making an explicit decision about the submitted message, with no unresolved current operation, may the caller send `{"op":"release_submission_hold","prompt_sha256":"HASH","operation_id":"ORIGINAL_OPERATION_ID","chat":"ORIGINAL_CHAT_AND_TAB_ID","history_rechecked":true,"reason":"SPECIFIC_RECORDED_DECISION"}`. The helper records that decision and permits a future prepare; it does not itself send anything. These are caller attestations, not browser verification. A corrupt hold record fails closed. New invocations of the old helper refuse unresolved submission holds; already-running old code and clients that disregard this protocol are not fenced.

Ten tasks may prepare prompts and await responses concurrently. Cooperating clients serialize browser input, send and verification. With `--wait`, a busy helper emits `WAITING` and keeps waiting without the previous 60-second acquisition cutoff. Monitor the running helper in bounded tool waits and continue automatically; `WAITING` is not a failure. Close stdin to cancel; early input while waiting is rejected. When the lock becomes available the helper emits `GRANTED`; immediately send `{"op":"activate"}` followed by a newline, then wait for `READY` or `NEEDS_INSPECTION` before opening or focusing ChatGPT. If the controller disconnects or fails to activate within 60 seconds, the unactivated grant is released; an activated owner is not timed out because browser actions cannot be fenced. The scheduler is not FIFO and can starve; a live but frozen activated owner or unresolved state can still block progress. Launch only when ready to act and do not leave acquired ownership unattended. The earlier `--wait-seconds` mode is an explicit bounded option, not the default workflow. Shared pointer/focus, older clients and noncooperating human actions remain outside this advisory lock. Do not claim independent tabs or exactly-once delivery without a safe isolated test.

The helper does not control or verify the browser, assert exactly-once delivery, fence in-flight actions, or detect invisible user edits. Its states only preserve the cooperating agent's attestations and enforce sequencing. Separate browser profiles may reduce interference only after an isolated, non-disruptive test; do not create accounts or modify profiles without a separate task. Never overwrite user drafts or modify the shared clipboard. Save the completed answer and record the visible send evidence as below.

## Wait when an unknown draft is visible

An unknown draft blocks input and consultation, not the entire task by itself. If the task-owned tab displays nonempty text that is neither this operation's exact saved prompt nor an identified recoverable agent insertion, do not type, clear, send, copy, or claim it. Record the task-owned tab ID and that the field was nonempty without recording the unknown content; release the shared lock by closing the helper's stdin. Keep the tab open and leave its field untouched.

Keep the task active rather than ending it solely because of the obstruction. While waiting, do only work that does not itself require the blocked consultation under root instructions, such as locating already-existing task inputs, checking saved receipts, or mechanical validation. Do not conduct new analysis, research, or creative development before the mandatory consultation. After a bounded interval (approximately 30 seconds), reacquire using `--wait`, activate the grant, and check the journal before refocusing the same task-owned tab. If the helper reports `NEEDS_INSPECTION`, follow recovery for that exact original operation only when its chat can be inspected without interfering with its owner; otherwise release and keep waiting. Do not bypass the marker or treat an empty other tab as proof. If the same field is now empty, continue the normal protocol. If any unknown text remains or appears, leave it unchanged, release the lock, and repeat while the task can continue. Never create replacement tabs merely to escape a draft and never hold the lock during the interval or while awaiting a response. Rechecking cannot guarantee progress: an already-open tab may retain an inherited draft even after its source changes, and another session can edit asynchronously. If the task-owned tab becomes inaccessible, a required user decision arises, or the session must end, preserve its continuation point and explain the exact blocker instead of claiming completion.

## Choose the model and reasoning mode

Model and reasoning effort are separate controls. Read each visible label independently immediately before sending a prompt, and record the exact labels in the task record when required.

- Choose the model the user requested, if it is available in the visible model menu. Do not infer model availability from a previous session, plan, or subscription label.
- Choose the reasoning mode the user requested, if it is available in the visible reasoning control. In this UI, reasoning effort is exposed through a labeled slider; use its visible label to confirm the result. The model menu also exposes a separate GPT-6 / GPT-5.6 Sol choice.
- When the user explicitly requests Pro or Extra High, select that mode in the UI. Do not claim that the mode cannot be changed merely because a different mode is currently selected. Do not equate Pro with a model name or treat Extra High as the skill's identity.
- For ytvideos' required personal consultation, use Extra High by default unless the user specifies another mode. A direct Pro request takes precedence. For other tasks, follow the user's requested mode; if none is specified and no project rule sets one, keep the current visible mode.
- Labels, available models, and control layout may change. Do not rely on remembered slider positions or instructions from a previous interface version. If the requested option is absent, disabled, or blocked, capture what the UI actually says and report that limitation without claiming a successful switch.
- The visible Russian label `Очень высокий` is the localized label for `Extra High`. Either confirms Extra High. Record the label as displayed.
- Before sending, confirm that the visible label corresponds to the requested mode, including its documented localization. If the mode is not visibly confirmed, do not send a prompt that depends on it.

Use one narrow request per consultation. Wait for the full answer, read it, and save the request, exact visible model/mode labels, URL, completed answer, and decisions in the task's record. Apply the relevant task skill's content and review requirements; this browser skill does not replace them.

## Save the completed response

Use supported browser UI observations to obtain the complete finished response as text, then write it directly to the task-owned project file with an available authorized file tool. Check that the captured text is complete and matches the visible response; record the source URL and verification. Long output may be truncated: do not claim a complete capture unless checked. Browser and file tools may be separate; no direct filesystem access from the browser runtime is assumed.

Do not open TextEdit or another user editor solely to transfer text. Do not use the shared clipboard when it would change or overwrite its contents; do not inspect, restore, or overwrite another session’s clipboard contents. Use a supported non-clipboard route where available. If complete text cannot be obtained and saved safely using supported tools, preserve the source and report the concrete blocker; do not bypass sandbox, browser or platform restrictions. A visible application remains appropriate when explicitly requested or required by the actual task or supported workflow, not as an automatic workaround.

## Verify inheritance between tabs

Do not assume a new tab inherits a model or reasoning choice. Check the visible label in each new chat before submitting. To verify inheritance as a test, use a separate agent-created tab with an empty composer, select a mode in the first test tab, then inspect the new tab before entering any content. Do not perform this test in a profile with active user sessions or unsent input. Record both observations and restore the original mode after a test if the preference is shared. If a clean isolated test is unavailable, say that inheritance is unverified.

## Close completed tabs

- Close only tabs created by the current task, and only after the answer is complete, the required record is saved, and the tab has no unsent input or unfinished work.
- In a multi-session review, close each completed task-owned tab as soon as its response is recorded and it is no longer needed, without waiting for the entire review cycle to finish. Start each required independent review in a new chat.
- Leave user-created or user-owned tabs open. If using a claimed user tab, release it without closing it.
- Close a task-owned tab only when its composer is empty. The shared composer procedure governs clearing drafts. Leave tabs with approval/login waits or unfinished work open.
- If work remains unfinished and the draft cannot be cleared safely, leave the tab open and identify the continuation point. Once the task is complete, clean up its own empty/completed tabs so obsolete ChatGPT pages do not accumulate.

## Limits and records

If Chrome, the requested model/mode, or the needed chat cannot be accessed, stop only the dependent consultation and report the concrete blocker. Continue independent work when possible. Preserve existing records; save a new consultation under `.agent/consultations/` for project-wide work or next to the episode for episode-specific work, using the project template. Record composer ownership/state, task ID, exact prompt, visible send confirmation, and whether the composer was empty at release. Do not inspect hidden application storage or rely on undocumented UI behavior.
