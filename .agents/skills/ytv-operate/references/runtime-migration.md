# Перенести сохранённый run на проверенную версию

Выполнять только по явному поручению владельца перенести этот выпуск. Это maintenance-операция над тем же run, а не создание нового выпуска, новое согласие на сценарий или разрешение тратить деньги. Контракт и команды — [migration](../../../../docs/migration.md#миграция-runtime-сохранённого-run).

1. На прежнем закреплённом checkout получить `status` → `next` → `plan`; сохранить точные root, run ID и version. Сверить существующие approvals, артефакты, операции и бюджеты. Старый `CURRENT_CONTEXT` — производное представление, не источник текущей версии. Незавершённые внешние операции сначала reconcile штатным способом; новые запросы не отправлять.
2. Подготовить проверенный target checkout с сохранёнными в Git code/rules и нужными контрактными тестами. Прочитать его skill/документы и новые требования. Сохранить доступным прежний checkout и медиа. Художественный профиль и уже принятые bytes этим маршрутом не меняются.
3. Выполнить `migrate-runtime plan` на target с точным `--source-root` и ожидаемой версией. Сохранить весь JSON. Проверить различие pins, сохранение профиля, approvals и стоимости, отсутствие активных leases/неопределённых operations и наличие всех нужных target references. До script approval допустим только pending script без outputs; кандидаты сохраняются без принятия и review не создаётся. Сам plan состояние не меняет.
4. По уже полученному решению пользователя выполнить `migrate-runtime apply` с exact plan и подлинными `--source`/`--message`. Повторного согласования неизменённого поручения не требуется. При несовпадении version/pins/входов не редактировать план вручную: прочитать фактическое изменение, подготовить новую проверку и удостовериться, что исходное поручение по-прежнему применимо.
5. Сохранить receipt, затем с target root получить `status` → `next` → `plan` и context нужного этапа. Сверить старые approvals/операции/расходы и hashes медиа. Обновить производные указатели продолжения через штатные команды. Миграция не означает повторную приёмку прежних кадров и не закрывает отсутствующий звук/финальный review.

Если в рамках того же действующего поручения нужен дополнительный локальный ремонт runtime, сначала проверить новую версию и подготовить новый plan от текущего закреплённого source. Для apply передать `--continue-receipt` с SHA-256 последнего migration receipt и неизменные подлинные `--source`/`--message`. После production-переходов подготовить новый plan на актуальное quiescent-состояние; сохранить исходные channel/format/intent, script approval и лимиты бюджета. Убедиться, что исходное поручение охватывает ремонт; флаг не является новым разрешением. Повтор exact apply сохраняет тот же parent receipt. Не придумывать новую ссылку на сообщение для обхода защиты повторов.

При откате использовать сохранённый исходный snapshot и его root для отдельной проверенной maintenance-операции. Нельзя просто заменить файл базы или pins: после миграции могли появиться новые артефакты, события и внешние действия.
