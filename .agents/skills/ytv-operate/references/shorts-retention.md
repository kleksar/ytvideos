# Разобрать удержание опубликованного Short

Применять к запросу о результатах конкретного опубликованного Short и улучшении следующего выпуска. Это отдельная read-only работа по [editorial](../../../../docs/standards/editorial.md#сигналы-аудитории-и-границы-вывода): не создавать production run, новый approval или расписание наблюдений. Разбор не меняет опубликованный ролик, принятый сценарий и правила канала. Для операций с существующим run сохранять его pins.

## Получить наблюдения

1. Установить точные channel ID и video ID, формат, дату публикации и длительность опубликованной версии. Прочитать профиль канала и связанный выпуск, если он сохранён. Название, похожая обложка и память сессии не подтверждают identity. Предоставленный экспорт/скриншот можно использовать без нового live-запроса, если его принадлежность ролику и окно понятны; неизвестное обозначить явно.
2. При разрешённом доступе через поддерживаемый Studio adapter выбрать проверенный канал → **Контент → нужный Short → Аналитика → Обзор/Взаимодействие → Удержание аудитории**. Сверить video ID в открытой странице. В доступных карточках или расширенном режиме читать метрики только с фильтром этого видео и нужного окна. Сохранить экспорт, если интерфейс его предлагает, либо снимок карточки/графика с фильтрами и фактически прочитанные значения. Аналитический connector/API использовать только через описанный read-only метод с нужными scopes; не придумывать endpoint и не считать публичные counters retention report. Платный provider требует действующего бюджета, его отсутствие не запрещает разбор предоставленных материалов.
3. Для каждого источника записать время получения с timezone, начало/конец окна, возраст видео к концу окна, доступный источник трафика, единицы и знаменатель метрики. Не объединять показатели разных окон. Сохранять определения из использованного отчёта: **stayed to watch** — выбор продолжить просмотр; **AVD/APV** — средняя длительность/доля среди продолживших; **engaged views** не включают циклы. Общие views, CTR обложки и число комментариев не заменяют эти показатели. Отсутствующее значение — `null`/`UNVERIFIED`, не ноль и не оценка.
4. Сохранить доступную кривую или наблюдаемые точки с их точностью. Если отчёт задаёт позицию долей длительности, переводить её в секунды по фактической длительности этой опубликованной версии и указать округление. Не восстанавливать кривую из APV, просмотров или ожидаемой формы. Данные удержания обычно обрабатываются 1–2 дня; это ориентир платформы, не срок готовности каждого отчёта. Если отчёт ещё отсутствует или выборка не позволяет вывод, сохранить ограничение и выполнить доступную часть без объявления причины провала. При отсутствии доступа назвать нужный отчёт/фильтр, не запрашивать credentials в чате.

## Сопоставить с роликом

5. Разделить начало, середину, payoff и петлю. Участок графика сопоставить с фактическим опубликованным видео или точно связанным MP4/таймлайном: что слышно, видно и что меняется в ожидании зрителя. Записать интервал, сцену/реплику/звук и источник сопоставления. При отсутствии точной версии можно описать метрики, но нельзя придумывать содержание участка или причину ухода. Мнение до публикации из MP4 review хранить отдельно от результата аудитории.
6. Сформулировать наблюдение и гипотезу раздельно. Просадка показывает место потери/пропуска, но не доказывает, что виновата музыка или конкретная фраза. Пик может означать интерес, повтор или непонимание. Если доступны комментарии именно этого выпуска, сохранить относящиеся к гипотезе примеры/IDs; число комментариев само по себе не доказывает удовлетворённость или дополнительный watch time. Не добавлять собственные комментарии ради проверки.
7. Сравнить с подходящими своими выпусками, если они доступны: тот же формат, язык/аудитория, сопоставимая длительность и возраст после публикации, с учётом трафика. Указать отличия и ограничение малой выборки. Не назначать универсальную норму «90%», не сравнивать APV роликов разной длины как равноценный результат и не выводить победителя по одному числу. Если подходящего сравнения нет, гипотеза остаётся предварительной.

## Передать следующий шаг

8. Выбрать одно проверяемое изменение следующего сопоставимого выпуска: конкретный способ показать начало, убрать повтор, согласовать визуальное раскрытие с репликой или изменить музыкальный акцент. Назвать, какое наблюдение его мотивирует и по каким доступным показателям будет оцениваться результат. Если данных для выбора нет, записать точный пробел вместо выдуманного улучшения. Несколько разных роликов не являются рандомизированным A/B; остальные изменения и различия аудитории ограничивают вывод.
9. Сохранить одну компактную заметку: **выпуск и версия; источники/окна/значения; наблюдаемый участок; сопоставление; гипотеза; следующий опыт; ограничения**. Экспорт/снимки сохранять рядом как evidence по [storage](../../../../docs/standards/storage.md). Для существующего run использовать текущий механизм supporting artifacts:

   ```bash
   uv run python -m ytvideos attach-artifact --run RUN_ID --file retention-observation.md --kind retention_observation --source REPORT_REFERENCE
   ```

   Подставлять реальный run и источник; без связанного run сохранить заметку в материалах выпуска, не создавать run ради прикрепления. Команда сохраняет bytes/provenance, не валидирует смысл и не добавляет заметку автоматически в task inputs. Передать следующий `research` явно по artifact ID/path; если вывод принят, включить его в новый research output с исходной ссылкой. Не переписывать завершённый research прошлого выпуска и не подменять pinned документы. Подробности хранения — [task contract](../../../../docs/operations/task-contract.md#источники-и-обложки).

Пользователю сообщить наблюдение, предел уверенности и конкретный следующий опыт либо недостающие данные. Применение процедуры не подтверждает рост удержания; это проверяется следующими публикациями. Применять такую же связь данных и гипотез к поиску бумажного самолётика, если он предусмотрен каналом, не добавляя игру всем форматам.
