# Карта маршрута выпуска

Общий порядок и полномочия принадлежат [production skill](../SKILL.md); этот файл задаёт запись и механическую проверку, не новый процесс и не разрешение на работу или публикацию. Для полного Paper/Nuviko-выпуска карта `FLOW_STATE.json` хранится в canonical-каталоге выпуска рядом с `CURRENT_CONTEXT.md`. Реестр и current context остаются входом; карта ссылается на существующие исходники, handoff, receipts и решения, не копирует их. Не создавать карты задним числом для чужих активных сессий. Для узкой задачи применять только её scope, не превращая её в полное производство. Канал Nuviko остаётся замороженным по root.

## Выбор входа

- `collaborative`: тему/сырой материал разрабатываем вместе; `develop_story` выполняет нужную сценарную процедуру и фиксирует существующее решение пользователя о принятии. Далее сохраняется производственный текст.
- `accepted_story`: пользователь уже принял сюжет, но нужен полный текст озвучки. Сохранить содержание и подготовить текст; не выполнять повторный фактчек или переписывать принятый сюжет без поручения. Не создавать новую точку одобрения.
- `ready_text`: готовый пользовательский текст для производства принимается как вход; готовый английский текст идёт в TTS дословно, русский адаптируется по общему языковому правилу. Не запускать новую разработку и не запрашивать повторное принятие.

Узкое поручение и явные более поздние указания имеют приоритет над предположением о полном flow. При создании карты зафиксировать точный источник входа, scope, формат и канал; новые разрешения из карты не возникают.

## Создание и ведение

Из корня проекта, после реестра, текущих материалов, канальных правил и согласования владельца работы с другими активными сессиями:

```sh
python3 .agent/scripts/episode_flow.py init /ABS/EPISODE/FLOW_STATE.json --episode EPISODE_ID --channel paper --format short --input ready_text
python3 .agent/scripts/episode_flow.py check /ABS/EPISODE/FLOW_STATE.json
```

`init` создаёт только отсутствующий файл; существующий не перезаписывает. Допустимые channel: `paper`, `nuviko`; format: `short`, `long`; input: три перечисленных значения. Скрипт создаёт применимую упорядоченную карту и владельцев, но никого не вызывает и ничего не производит. Обязательные консультации и профильные навыки определить по root, этапу, входу и реальному scope; запись навыка не заменяет его чтение и выполнение. В маршрутной карте `skill_runs` для каждого перечисленного владельца фиксировать `APPLIED` с реальной ссылкой на результат либо `N_A` с обоснованием; при частичном этапе оставить `PENDING`/`BLOCKED`. Хранить дополнительные применимые навыки и консультации в evidence этапа/существующем handoff. `N_A` не отменяет обязательных требований навыка.

Для каждого этапа сохранять `status` (`PENDING`, `DONE`, `BLOCKED`, `STALE`), `artifacts` с абсолютными `path`, `version`, `sha256`, `dependencies` с абсолютными `path`, `sha256`, и `checks`: `name`, `status` (`PASS`, `FAIL`, `UNVERIFIED`, `N_A`), `reviewer`, `method`, `coverage`, `evidence`. Для PASS/FAIL/N_A заполнить все поля и указать действительное свидетельство/обоснование; `UNVERIFIED` не повышать до PASS по хэшу или успешной команде. Включать все существенные входы и зависимости, в том числе принятый текст, профиль, звук, изображения и нужные records по фактическому этапу; указывать только реальные зависимости. Состояние/версии скрытых или удалённых ресурсов не выводятся из имени. Зафиксировать `input_evidence`, `scope`, `next_step`, а в `decisions` — только реальные пользовательские решения с `accepted: true`, `target` (точная версия/хэш/выбор) и `evidence` (ссылка на сообщение/квитанцию). Ключи: `story_accepted` только для совместной разработки, `mp4_accepted`, `packaging_accepted`, `unlisted_accepted_and_release_choice`. Последний target должен содержать конкретный выбор пользователя, а не подразумеваемое согласие. Выбор названия и обложки независим. Это существующие контрольные точки, не дополнительные approvals.

Для обновления сначала сохранить кандидат JSON отдельно, прочитать и сверить текущий файл и хэш, затем:

```sh
python3 .agent/scripts/episode_flow.py update /ABS/EPISODE/FLOW_STATE.json /ABS/CANDIDATE.json --expected-sha256 CURRENT_SHA256
python3 .agent/scripts/episode_flow.py check /ABS/EPISODE/FLOW_STATE.json
```

`update` проверяет структуру и сравнивает хэш под общей блокировкой совместно использующих этот CLI сессий; изменившийся файл не перезаписывается. При конфликте перечитать и согласовать изменения, не делать слепой повтор. Блокировка не защищает от программ, которые её игнорируют: один владелец записи и координация с активными сессиями обязательны. `CURRENT_CONTEXT.md` держать кратким и обновлять по фактам; карта и существующий upload receipt не подменяют друг друга.

## Плейлист при загрузке

В handoff упаковки сохранить результат свежей проверки плейлистов канала: timestamp/источник, target channel ID, подходящий playlist ID и основание либо конкретное предложенное название и причину, статус решения и следующий шаг. При недоступности записать `UNVERIFIED`, не выдавать за отсутствие подходящего плейлиста. Карта может хранить этот независимый результат в дополнительном объекте `playlist_resolution` или ссылке на версионированный handoff; не превращать отсутствие ответа о новом плейлисте в новую блокировку завершения упаковки/загрузки. Для недоступной проверки оставить открытый пункт в этом объекте/handoff, а не подменять его PASS/N_A. До выполнения добавления при возобновлении повторно сверить свежий video ID, playlist ID и membership; после операции записать фактический read-back, сохраняя privacy и видимость. Создание нового плейлиста требует необходимого разрешения.

Для новых Shorts карта автоматически включает `ytv-shorts-story` при разработке текста и `ytv-shorts-loop` для оценки перехода; готовый пользовательский текст не требует сценарной переработки. Для старой ещё не выполненной карты, в которой этих владельцев нет, перед продолжением сверить и обновить список текущего этапа через обычный `update` с проверкой хэша; не переписывать принятый сюжет. Уже выполненный по старой карте этап сохраняется как исторический результат с предупреждением, без фиктивного утверждения, что новые skills тогда применялись. При новых действиях соблюдать действующий scope и правила.

## Возобновление и пределы проверки

`check` только читает, сверяет путь/хэш зарегистрированных артефактов и зависимостей, последовательность, свидетельства, существующие решения и применимую карту. Выводит структурные ошибки, затронутые `stale` и ближайший `ready`; ничего автоматически не запускает, не записывает и не даёт подтверждений. При изменении файла отмечает соответствующий этап и прослеживает только явно записанные связи с артефактами. Неполная карта зависимостей ограничивает результат: на возобновлении вручную сверить профиль, версии, фактические пользовательские решения, внешнее состояние и фактические входы владельца этапа. Изменённую часть и зависящие от неё результаты перепроверить; неизменённые не перезапускать. `ready` не означает разрешение игнорировать блокировку канала, действующий scope, отдельные требования tools, ограничения среды или обязательный `VIDEO.mp4.delivery.json` перед upload. При конфликте или неизвестном внешнем результате сначала выполнить read-back; независимую работу продолжать.

Проверки означают только то, что фактически зафиксировано. Машина не устанавливает качество текста, изображения, звук на слух, подлинность пользовательского одобрения, права или результат YouTube. Перед `DONE` координатор применяет реальный профильный skill и заносит его фактический handoff. Не изобретать PASS, массовый N_A или новые пользовательские запросы. Передача MP4, упаковка, ссылка Unlisted и публикация сохраняют уже действующие контрольные точки и полномочия production flow.
