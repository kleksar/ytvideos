# Найти историю и написать полный текст

До действий выполнить [общую процедуру](../ytv-start/references/task-execution.md). Для `research` и `script` прочитать профиль, [editorial](../../../docs/standards/editorial.md), [thumbnail promise](../../../docs/standards/thumbnails.md) и [формы начала](references/hook-patterns.md); на `script` также [narration](../../../docs/standards/narration.md). Читать полные pinned тексты и точные входы; соблюдать бюджет. CLI/outputs/receipts принадлежат [task contract](../../../docs/operations/task-contract.md).

Различить вход по [workflow](../../../docs/workflow.md#готовый-текст-и-набросок). **Полный source с явным поручением производить не проходит авторский цикл повторно:** координатор [импортирует](../../../docs/workflow.md#принятый-источник-без-повторной-редакции) точные bytes и решение владельца. Новый сюжет/содержательная переработка требуют [трёх версий одной истории](../../../docs/standards/editorial.md#версии-на-2-5-и-10-минут); узкая проверка, идеи и техническая правка не расширяют scope. Шаги 1–4 — `research`, 5–7 — `script`.

Для `music_first` результат — [typed edit plan](../../../docs/operations/task-contract.md#outputs): принятый вариант, ordered segments и реальные вокальные слова либо пустая речь instrumental. Исследовать запись/права и визуальное развитие, не добавлять narration ради правила длительности. Другие edit-рецепты сохраняют контракт; нехватка исходников/прав — blocker.

1. Прочитать историю тем/углов, отказы владельца и доступные наблюдения удержания. Определить аудиторию, причину смотреть и ограничения. Отделять спрос от гипотез; простота производства не доказывает интерес.
2. При самостоятельном поиске выполнить [отбор](../../../docs/standards/editorial.md#отбор-до-полного-сценария): разные истории → проверенные заявки → сравнение с сильнейшей альтернативой. Для каждого финалиста проверить «почему остановится / останется / что получит» и сильное возражение. При заданном замысле исследовать его, не выбирать другую тему. При отказе сохранить причину; расписание не обязывает создавать слабый PR/Issue или фиктивный `selected_topic`.
3. Сохранить один research: фактическую выборку, сравнение, источники/места, неопределённость, дубли и спрос отдельно от предположений. Использовать принятый research из `inputs`, не повторять поиск для каждой версии; новые утверждения проверять отдельно.
4. Определить thumbnail promise/payoff: аудитория, verified объект/факт, вопрос, настроение, первое подтверждение и полный ответ. Передать packaging заметку через supporting artifact/ID/path, не поля strict ReleaseSpec. Таймкод уточнить по монтажу. Для трёх длительностей наметить собственные смысловые шаги и добавочную ценность, сохраняя одну историю.
5. Определить язык production master по [audio](../../../docs/standards/audio.md#речь-и-голос), не по языку входа или review-перевода. Написать **три полных текста** и применимые полные переводы по [пакету](../../../docs/standards/editorial.md#пакет-одной-истории), не обрезки одного master. Для каждой версии: отдача → вопрос → начало/конец → причинная середина → [устная редактура](../../../docs/standards/narration.md#порядок-правки). Сохранить baseline при переработке. Long начинает с [обещания/вопросов](../../../docs/standards/editorial.md#обещание-в-начале-long); повествовательный Short с `narrative_loop: required` даёт развязку до естественной петли. Проверить единый смысл языковой пары. Не растягивать слабую версию и не выдавать оценку длительности за измеренную озвучку.
6. Выполнить авторскую проверку каждой редакции и [ограниченный independent review](../../../docs/standards/editorial.md#ограниченный-review) точных текстов. Получить [свежего reviewer](../../../docs/operations/task-contract.md#доступ-к-независимому-reviewer), без авторских оценок/диагноза: начало, весь текст, источник после первого чтения. Для narrative Short — весь текст два раза и буквальный стык. Проверить факты, причинность, viewer value, payoff и формат; после чтения всех редакций сравнить добавочную ценность длины и рекомендовать сильнейшую, включая короткую. Записать отдельные оценки/недостатки/hash в story-review, не менять receipt schema. `revise` исправлять в разрешённом scope и бюджете; новый hash требует нового review. Reviewer может отвергнуть тему; недоступный review — UNVERIFIED, не авторский PASS.
7. Сохранить пакет по [контракту вариантов](../../../docs/operations/task-contract.md#outputs). Для предлагаемого runtime master подготовить input helper-командой из [receipt](../../../docs/operations/task-contract.md#receipt); reviewer сам сохраняет `ytv-script-review-v1`, ответ не дописывать за него. `independent_review` и применимый `narrative_loop` ссылаются на один его ответ. Показать все полные версии/переводы, сравнение, рекомендацию и ограничения; один exact master передать на script gate, не одобрять его и не запускать три производства. Принятый source вернуть координатору без фиктивного повторного review.

## Сюжетные PR и переработка

Точка входа агента очереди использует тот же стандарт одной истории и трёх длительностей. Поручение создать или переработать очередь разрешает редакционные изменения, но не merge, media, upload или публикацию.

1. Прочитать свежий remote main, этот skill, editorial/narration, профиль, существующие PR и решения владельца. Новый PR вести от актуального main; существующую историю менять в её ветке без force-push и дубликатов. Перед записью повторно сверить head; чужую незавершённую работу не перезаписывать.
2. Выполнить шаги 1–7 в применимой области. Для старой истории сначала открыть полные тексты/research и сохранить baseline commit/path/hash; оставить сильную подходящую версию и написать недостающие. Синхронизировать зависимые ссылки, spans и review. Принятый/производимый master и отвергнутые темы защищены [правилом очереди](../../../docs/standards/editorial.md#существующая-очередь).
3. По умолчанию использовать сохранённый run. Когда владелец отдельно разрешил Git-only редакционную очередь без доступного runtime, обозначить PR/README/handoff `EDITORIAL_CANDIDATE_UNREGISTERED`: это не официальный script gate. Сохранить реальные недоступные capabilities и путь переноса; не выдумывать run, reviewer, receipts или approvals. Это исключение не разрешает обычному production worker обходить runtime.
4. В одном PR разместить таблицу трёх длительностей, полные тексты, сравнение/рекомендацию и реальные статусы. В existing PR/progress записать обработанные версии/hash, blockers и следующую непроверенную работу. За запуск делать ограниченный бюджетом набор и продолжать с него; не объявлять всю очередь переработанной и не создавать PR только ради таймера. Проверить remote read-back и CI точного HEAD, отделяя проверки структуры от художественного качества.

Prompt планировщика хранит repo, каналы, scope, расписание и эту точку входа; художественные требования читает из репозитория, а не поддерживает вторую копию. Новые требования в открытом MR не выдавать за уже слитый main: до merge их применение возможно только как явно сохранённое прямое поручение владельца с точной ссылкой на proposed revision. Внешний scheduler обновлять и проверять отдельно.

Служебную attribution не включать в narration; существенную неопределённость сохранять. Обновлять только зависимые результаты.
