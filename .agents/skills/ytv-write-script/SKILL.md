# Найти историю и написать полный текст

CLI и точные outputs/receipts: [task contract](../../../docs/operations/task-contract.md).

Прочитать task context, профиль канала и [editorial](../../../docs/standards/editorial.md). Если запрос узкий, сохранить его scope. Работать с закреплённой ревизией и доступным бюджетом.

Сначала различить вход: поиск темы, заданный сюжет/набросок или точный готовый production script — по [workflow](../../../docs/workflow.md#готовый-текст-и-набросок). На task `research` выполнять подходящий scope проверки и отбора. На task `script` использовать принятый research из `inputs`, не запускать новый выбор темы без конкретного выявленного дефекта. Готовый присланный текст проверять без самовольной переработки; его пользовательское принятие регистрирует host, не авторский receipt.

1. Прочитать историю тем/углов и отказы владельца. Определить конкретную аудиторию и её причину смотреть. Источники и удобство производства сами по себе не являются основанием выбора.
2. Только при самостоятельном поиске темы выполнить [отбор до полного сценария](../../../docs/standards/editorial.md#отбор-до-полного-сценария): разные истории → короткий список проверенных заявок → сравнение с сильнейшей альтернативой. Проверить «почему остановится / останется / что получит» и возражение к каждому финалисту. При заданном замысле исследовать его; при готовом narration проверять точный текст без отбора новой темы. Если достойного кандидата нет, сохранить отказ в research notes; не создавать сценарий/PR/Issue ради расписания и не выдумывать `selected_topic`.
3. Сохранить в существующей исследовательской записке фактическую выборку, сравнение, выбранный угол, аудиторию, источники/места, неопределённость, пересечения и сигналы спроса отдельно от гипотез. Не выдавать самооценку за прогноз просмотров. Успешный `research` заканчивается проверенным выбором при поиске либо проверкой заданной истории, затем перейти к `script`; отказ не помечать успешным результатом.
4. Рано определить thumbnail promise/payoff: целевой зритель, verified объект/факт, обещание одним предложением, открытый вопрос, ожидаемый жанр/настроение, первое подтверждение в кадре/реплике и отдельный полный payoff. Выбрать конкретную причину интереса по [thumbnail standard](../../../docs/standards/thumbnails.md); при использовании референса связать его переносимый приём с фактом своего сюжета и отметить узнаваемый предмет/действие интро для будущей обложки. Заметка остаётся вне narration и strict packaging JSON. Её можно сохранить внутри research output, доступного через `supporting_inputs`; отдельный файл передать packaging явно по artifact ID/path. Для сценария отметить сцену, точный timecode уточнить после монтажа.
5. При написании или разрешённой переработке пройти порядок проектирования из [editorial](../../../docs/standards/editorial.md): отдача → главный вопрос → начало/конец → причинная середина → устная редактура → первый слушатель. Применить общий драматургический каркас к формату канала; при переработке сохранить исходник и сравнить его сильные функции с новой версией. Сохранить компактное evidence в существующих research/script артефактах. Для каждого Short обязательна естественная петля с ответом до повтора; она проверяется после развития, кульминации и развязки. Long не обязан зацикливаться.
6. Проверить точный текст по [ограниченному review](../../../docs/standards/editorial.md#ограниченный-review): ожидание от начала, его развитие, решающая реплика/сцена и отдача; отдельно факты/модель, подразумеваемая причинность и конец → начало. Проверить первое подтверждение обещания обложки, ожидаемый тон и прямой payoff. Не объявлять бумажную оценку длительности измеренной озвучкой. Использовать свежего независимого reviewer; передать текст без подсказки ожидаемой оценки, исходник — после первого чтения. Попросить назвать причину досмотра и точное место потери интереса; reviewer может отвергнуть тему, а не только поправить фразы. Исправить реальные дефекты в пределах scope и attempts/time budget. При самостоятельном поиске слабый замысел вернуть к отбору; дефект принятого текста показать конкретно, не подменяя его другим сюжетом. Невыполненный review сохранить UNVERIFIED. Подробные scene prompts и сюжетный PR не готовить вместо этой проверки.
7. Сохранить полный текст и output receipt через task contract. Для повествовательного Short обязательный `narrative_loop` связывает точные крайние реплики, их соединение и независимый review с hash этого сценария; тематическое возвращение без естественного продолжения не проходит проверку. Показать пользователю текст целиком, для англоязычного выпуска — также полный русский перевод, краткую формулировку ценности и только существенные ограничения. Для нового или изменённого текста остановиться на script gate. Для exact текста, уже переданного в производство, host регистрирует исходное решение без повторного вопроса; при техническом blocker сохранить результат и указать его. Не показывать одно меню тем вместо требуемого сценария.

Внутренние sources и служебные attribution не добавлять в публичный текст; существенную неопределённость не скрывать. Явно принятый сценарий не переписывать под видом технического шага. При порученной правке сохранять точные version/hash и обновлять только зависимые результаты.
