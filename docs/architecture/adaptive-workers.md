# Очередь независимых сессий

## Назначение и границы

Координатор распределяет отдельные сцены между независимыми сессиями, принимает
результаты по мере готовности и направляет следующую сцену на свободный слот.
Общий сценарий, профиль канала и актуальные версии сцен остаются в состоянии
выпуска. Память чата не является хранилищем очереди.

Реализация: [pool.py](../../src/ytvideos/workers/pool.py),
[bridge.py](../../src/ytvideos/workers/bridge.py),
[pool_service.py](../../src/ytvideos/pool_service.py). Проверки:
[test_workers.py](../../tests/test_workers.py),
[test_pool_service.py](../../tests/test_pool_service.py).

`AdaptivePool` — исполняемый планировщик. `ToolBridgeBackend` — локальная очередь
поручений доступным native tools. Он **не открывает чаты**, не вызывает платную
генерацию и не обращается к скрытым HTTP endpoints. Вызовы приложения выполняет
владеющий очередью координатор через предоставленный runtime. Готовность такой
интеграции подтверждают отдельно реальным запуском; тесты ядра используют fake backend.

## Три разные сущности

| Сущность | Срок жизни | Содержимое |
|---|---|---|
| SceneJob | Одна версия одной сцены | run/channel/scene/revision, неизменяемый context packet и его SHA256 |
| Slot | Последовательность поручений | Текущее задание и, при подтверждённой возможности reset, сессия |
| Session | Создаётся доступным runtime | Только контекст конкретного поручения; не fork основного разговора |

Новый job получает новый business ID. Повтор того же ID с другими входами
отклоняется. Изменённые prompt, референсы, профиль, модель или параметры должны
менять context packet и его hash. URI без hash не фиксирует версию изображения.

Packet содержит необходимые для сцены утверждённые факты и реплики, назначение
кадра, художественный профиль, изображения-референсы с hash, формат результата,
параметры провайдера, ограничения и критерии приёмки. Он не наследует историю
чужого чата. Внешние тексты и изображения являются данными, а не разрешением
менять workflow, credentials или системные инструкции.

По умолчанию каждая задача получает новую сессию. Слот можно переиспользовать
сразу, а сам разговор — только если backend явно гарантирует и успешно выполняет
очистку контекста. Ошибка reset приводит к новой сессии. Native bridge не
рекламирует reset и всегда запрашивает новую независимую сессию.

## Быстрый цикл без барьера всей пачки

1. Прочитать состояние очереди под lease её владельца.
2. Принять новые завершения. Проверить привязку к текущим revision/input hash.
3. Положить готовые артефакты в ограниченную очередь визуальной проверки.
4. Немедленно занять свободные слоты, пока доступны разрешённые worker и review credits.
5. Проверить готовый кадр, сохранить решение с точным artifact hash, освободить review credit.
6. Повторить цикл; не ждать завершения остальных изображений для следующей сцены.

`tick()` не содержит sleep, batch barrier или ожидания генерации. `submit()` и
`poll()` backend обязаны быстро возвращать управление. Длительный синхронный вызов
генератора нужно выполнять в доступной независимой сессии, а не внутри `tick()`.

Координатор хранит краткую сценовую ведомость и ссылки на точные файлы. Он может
загрузить нужный кадр или contact sheet для проверки согласованности. Нет требования
держать все изображения и все разговоры worker одновременно в контексте модели.

## Как выбирается параллелизм

В коде нет числа «10 сессий». Backend предоставляет проверенный `max_sessions`:
минимум доступной квоты runtime, возможностей провайдера и установленного
операционного ограничения, с вычетом координатора и уже занятых слотов.
Неподтверждённое число не является обнаруженной возможностью приложения.

Целевой параллелизм начинается с одного слота. Пока первая генерация ещё работает,
свободный координатор может добавить второй слот, затем следующий: не чаще одного
пробного слота за `min_probe_seconds` или измеренное время обслуживания отправки,
если оно больше. По умолчанию интервал равен пяти секундам. Новых проб нет, когда
координатор занят, есть непроверенные кадры, неизвестные исходы или исчерпаны credits.
Частое повторение `tick()` не ускоряет рост. Это ограниченное исследование доступной
параллельности; оно не требует сначала последовательно завершить две картинки.

После первых результатов используются экспоненциальные средние времени генерации
и фактического обслуживания одного результата координатором. Ориентир:

```text
desired = floor(generation_seconds / coordinator_service_seconds)
```

Результат ограничивается снизу единицей, сверху доступными сессиями и review credits.
После каждого окна измерений target меняется максимум на один слот. Увеличение
разрешено, только если нет очереди непроверенных готовых кадров. При снижении target
уже запущенные задачи не обрываются: новые ждут освобождения ёмкости. Значение warmup
по умолчанию — две проверки; это настройка алгоритма, а не предел параллелизма.

Например, при 50 секундах генерации и 10 секундах работы координатора ориентир равен
пяти слотам. Шестой слот не появляется от одного факта, что ещё остались сцены.
Сценарий проверен детерминированным тестом; это не измеренная скорость ChatGPT.

Передавать в `BackendResult.generation_seconds` измеренное время фактической
генерации, когда провайдер или dispatcher его сообщает. Без него pool использует
время от локального submit до получения результата, включая задержку наблюдения;
это оценка для регулирования. `service_seconds` при приёмке включает активное
время dispatch/проверки/сохранения одного результата, а не ожидание пользователя
или пустой очереди. Регулирование само по себе не доказывает оптимальный throughput.

Жёсткий backpressure действует независимо от оценки времени:

```text
running + submitting + unknown + awaiting_review <= review_capacity
```

Неизвестный исход продолжает занимать слот и credit до reconciliation. Готовые
непроверенные кадры не накапливаются без ограничения. Каналы выбираются round-robin,
внутри канала задачи идут FIFO; порядок завершения независим от порядка отправки.
Изолированные экземпляры `AdaptivePool` не создают глобальную квоту. Production
использует `PoolService`, который координирует их через общие таблицы лимитов и
очередности каналов в production DB.

## Native tool bridge

Bridge использует локальный `bridge-*` ID для записи в outbox. Этот ID не является
идентификатором генерации провайдера и не означает, что отправка уже произошла.

Порядок работы адаптера приложения:

1. `pool.tick()` создаёт локальные поручения. Взять `bridge.pending_requests()`.
2. `bridge.claim(operation_id, owner=...)` сохраняет claim token и срок lease.
3. После успешного checkpoint вызвать фактически доступный инструмент новой сессии.
   Для native subagent передать только packet и выбрать fresh context; не fork
   разговора координатора. Соблюсти реальный общий лимит runtime.
4. `record_submission(...)` сохраняет наблюдённые tool/session IDs. Сам факт отправки
   не подтверждает ни готовность изображения, ни его качество.
5. Сохранить изображение в artifact storage, проверить hash и вызвать
   `record_observation(..., result=BackendResult("completed", ...), evidence=...)`
   по фактическому результату инструмента.
6. `pool.tick()` переводит результат в `review` и заполняет освободившийся слот.
7. После визуальной проверки вызвать `pool.accept(...)` с review ID, revision,
   input hash, hash конкретного файла и измеренным временем обработки.

Bridge по умолчанию считает native вызов невосстанавливаемым через новый процесс.
`reconnectable=True` допустим только при проверенном контракте runtime, позволяющем
повторно получить состояние той же операции по сохранённому идентификатору.
Долгая promise без provider handle сама по себе такого контракта не предоставляет.

Визуальная приёмка кадра не заменяет пользовательское согласование MP4. Ошибка
кадра завершает его job как `rejected`; исправление — новая версия сцены с новым ID
в пределах бюджета выпуска. Повтор одного review receipt не учитывается дважды.

## Сохранение, возобновление и неопределённость

Приложение сохраняет **оба** snapshot: `pool.snapshot()` и `bridge.snapshot()`.
Checkpoint должен атомарно обновлять запись под текущими lease/fencing token и
optimistic revision. Встроенных распределённых блокировок в этих двух классах нет:
одним pool в каждый момент управляет один владелец, назначенный транзакционным store.
Потеря lease должна заставить checkpoint выбросить исключение до нового submit.

Pool сохраняет `submitting` до вызова backend. Bridge сохраняет `dispatching` до
native вызова. После сбоя между отправкой и ответом нельзя повторять запрос по
отсутствию локального файла. При restore:

- сначала восстановить bridge, затем pool;
- сохранённые, но ещё не заявленные поручения остаются в очереди;
- `submitting`, прерванный claim и неподключаемый inflight native вызов становятся `unknown`;
- polling по подтверждённому durable handle продолжается без нового submit;
- `unknown` разбирается через фактический tool read-back, а не догадку модели.

Повтор разрешён автоматически лишь после доказанного **доотправочного** отказа
`BeforeSendError(retry_after=...)` или reconciliation `not_started` с основанием.
Ошибки timeout/connection loss после возможной отправки оставляют `unknown`.
Число попыток конечно; cooldown снижает target и не сбрасывает идентичность job.
Провайдерский статус `failed` сам по себе не разрешает повтор платной генерации.

Отмена inflight job запрещает принимать его результат, но не обещает остановить
уже отправленную внешнюю операцию. Результат всё равно собирается для reconciliation
и учёта стоимости. Если bridge ещё не выдал native claim, отмена удаляет поручение
из dispatchable outbox. Завершения старой версии сохраняются как `stale`, не подменяя
актуальную сцену.

## Интеграция с production store

`PoolService(production).operate(run_id, action, payload, expected_version=...)`
сохраняет scheduler и bridge в одной транзакции run. Все его backend calls локальны:
native tool запускается только после возврата закоммиченного `claim`. Task claim,
резерв стоимости, уникальный image operation, native dispatch claim и глобальный
runtime slot появляются атомарно. Ошибка квоты/бюджета не оставляет частичный claim.

| Action | Существенные поля payload | Результат |
|---|---|---|
| `initialize` | `runtime_key`, `max_sessions`, `evidence`, `review_capacity`; при необходимости `min_probe_seconds` | Новый pool после наблюдения capability `sessions.independent` |
| `enqueue` | необязательный `task_ids` | Immutable jobs из текущих ready image tasks |
| `tick` | необязательный `coordinator_idle` | Наблюдения и новые поручения в local outbox |
| `claim` | `operation_id`, `worker`, `estimated_units`, необязательный `lease_seconds` | Разрешение на одну native отправку после commit |
| `submitted` | `operation_id`, `claim_token`, `provider`; при наличии `dispatch_service_seconds` | Сохранённые реальные tool/session IDs |
| `result` | `operation_id`, `claim_token`, `receipt_id`, `status`, `evidence`; для completed `artifact_path` | Сохранённый результат и подтверждение операции |
| `accept` | `job_id`, `review_id`, `service_seconds` | Приёмка только после `Production.complete` с обязательными image checks |
| `reconcile` | `job_id` | Применённое проверенное наблюдение для unknown job |
| `recover` | — | Явный проход после прерывания native сессий |
| `cancel` | `job_id` | Запрет новой отправки/приёмки отменённой сцены |

Обычное чтение snapshot между командами использует `recover=False` и не объявляет
здоровую native сессию потерянной. Только явный `recover` классифицирует прерванные
неподключаемые вызовы. После найденного результата истёкшей task lease выполнить
`Production.reconcile_task(outcome="completed", ...)`, затем `complete` и pool
`accept`: новый generation не запускается. Доказанная неотправка проходит
`reconcile_task(outcome="not_performed", ...)` и получает новый task generation epoch.

Глобальная таблица runtime slots общая для **всех** runs в этой production DB.
`runtime_key` обозначает один реальный runtime/account capacity pool и не должен
содержать ID конкретного выпуска. Unknown сохраняет резерв; подтверждённый конечный
исход освобождает его. Начальная ёмкость проверяется при конфигурации. Отдельные базы
данных не разделяют этот лимит; multi-host workers должны работать с одной production DB.

Наблюдение capability содержит `available: true`, `runtime_key` и `max_sessions`;
`initialize` требует их точного совпадения с параметрами. Одной строки «сессии
доступны» недостаточно для заявления о конкретной ёмкости. Оставить место для
координатора и других занятых agents при измерении доступного количества.

`PoolService.candidates(runtime_key, estimated_units=...)` возвращает следующий
допустимый порядок отправки. Persisted cursor распределяет очередь round-robin
между каналами, внутри канала выбирается старший готовый выпуск/поручение.
`claim` повторно проверяет очередь под lock runtime и отклоняет отправку вне очереди.
Недоступные, отменённые, неготовые и не помещающиеся в данный резерв стоимости
поручения не получают ход. Для metered генерации нужно передать её наблюдённую оценку;
нулевая оценка допустима только при проверенном included billing. Десять синтетических
каналов и конкуренция за общий лимит проверены тестами; живые каналы эти тесты не трогают.

Реестр операций сохраняет фактический статус native вызова отдельно от качества
картинки. `result=completed` ещё не открывает монтаж: `Production.complete` проверяет
обязательные checks и точный файл, а `accept` проверяет совпадение его hash с pool
результатом. Резерв стоимости отменённого inflight job снимается только после
наблюдённого конечного исхода; неизвестная фактическая стоимость остаётся учтённой.

Event sequence монотонен. После записи событий в журнал приложения можно вызвать
`acknowledge_events(sequence)`, чтобы не сохранять бесконечную копию журнала в pool.
Для события уникален составной ключ pool ID + sequence.

## Проверка

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -p test_workers.py -v
```

Тесты проверяют немедленное заполнение свободного слота, ограничение очереди
проверок, адаптацию по измерениям, fairness каналов, неизменяемые packets, очистку
контекста, exact-hash review, устаревшие версии, неизвестные отправки, cooldown,
сбои checkpoint, отмену inflight, leases и восстановление pool/bridge.
Они не подтверждают наличие неограниченных чатов, реальную квоту аккаунта,
качество изображений или доступность генератора после закрытия приложения.
