# Разработка и проверка

## Рабочий цикл

1. Прочитать root и canonical owner изменения. Проверить ветку, upstream и состояние дерева по порядку ниже; учесть чужие изменения. Исправление ошибки начать с воспроизведения и причины.
2. Основная ветка проекта — `main`. По умолчанию работать с актуальным `main`; если для задачи нужна отдельная ветка, ответвить её от актуального `main` и сразу открыть PR в `main` по порядку ниже. Использовать небольшие тематические commits; этапы реализации могут идти отдельными заданиями/сессиями.
3. Детерминированные проверки и переходы реализовать кодом. Параметры канала держать в ChannelSpec; не добавлять hardcoded перечень имён в workflow.
4. Синхронно переписать действующую документацию и ссылки в актуальном состоянии, удалив отменённый путь. Историю изменения хранит Git. Task-specific очереди/разрешения и архивные evidence сохранять отдельно от production context.
5. Запустить адресные tests и обязательный общий gate. Прочитать diff. В MR описать проблему, изменение поведения, реальные проверки и оставшиеся runtime/migration ограничения.
6. Синхронизировать рабочую ветку с upstream по порядку ниже. Для каждой отдельной ветки поддерживать PR в `main` до слияния; merge выполнять после проверки и с учётом полномочий. Не менять production infrastructure/каналы ради подтверждения unit tests.

## Git и совместная работа

Это постоянное правило для всех агентов и задач этого репозитория: результаты совместной работы должны быть сохранены, а опубликованная рабочая ветка — синхронизирована с локальными коммитами. Явные ограничения пользователя, среды и требования проверки имеют приоритет.

1. В начале и перед окончанием задачи проверить корень репозитория, текущую ветку и её upstream, `git status --short --branch`, staged/unstaged/untracked и изменения других участников. Получить актуальное состояние `origin/main` перед новой работой и сверять с ним базу; не считать старый remote-tracking ref доказательством актуального сервера. Только для чтения и без изменений коммит не нужен.
2. Установить границы своей работы и владельца уже существующих изменений. В общем checkout не переключать ветку, не перезаписывать, не прятать и не коммитить незавершённые изменения другого участника. При параллельной работе использовать отдельную ветку/worktree, когда это безопасно и доступно; иначе координировать общие файлы и staging. Перед коммитом читать staged diff, добавлять точные пути или hunks; не применять вслепую `git add -A`, `stash --all`, `reset --hard` или `clean` к общему дереву.
3. Код, профили, правила, небольшие нужные текстовые материалы, права и receipts сохранять в Git с учётом [storage](standards/storage.md). Секреты, credentials, медиа и воспроизводимые временные результаты не коммитить. `.gitignore` поддерживать адресно по фактической роли файлов: проверить совпадения и исключения, не скрывать исходники, evidence и активные данные ради чистого статуса. Игнорирование не удаляет файлы и не создаёт резервную копию; уже tracked файлы от него не перестают отслеживаться. Перед добавлением проверять состав, размер и возможные секреты; не публиковать неразобранные данные массово.
4. Завершённые и проверенные изменения своей задачи группировать в понятные коммиты, не включая чужую работу. По постоянному поручению пользователя самостоятельно отправлять их в соответствующую удалённую ветку после проверок; не публиковать секреты, черновики или иные данные за пределами разрешённого scope. Использовать авторизованный для репозитория Git remote или GitHub connector текущей среды. Локальный SSH-профиль не является обязательным требованием к другой среде; не искать и не переносить чужие credentials.
5. Перед push сверить destination, upstream и фактическое состояние remote. При расхождении безопасно получить изменения и интегрировать их без потери локальной или чужой работы; не применять force push, переписывание опубликованной истории или разрушительные операции без отдельного прямого поручения. Если интеграция блокируется чужой работой или конфликтом, сохранить результаты, выполнить независимую часть и сообщить конкретную причину.
6. После push сверить локальный `HEAD` с фактическим remote ref и снова проверить status. Цель — чистое дерево своей области и совпадающие локальный и удалённый коммиты; чужую незавершённую работу сохранять и отдельно сообщать, если она делает общий статус нечистым. В отчёте указывать ветку, результат синхронизации, оставшиеся изменения и ограничения, в том числе игнорируемые локальные единственные копии, если они существенны.
7. `main` — общая основная ветка. Если работа ведётся в отдельной ветке, сразу после её первого содержательного коммита и push создать PR в `main`, не откладывая до завершения задачи; пока работа или проверки не закончены, открыть draft PR. Продолжать дополнять тот же PR, поддерживать описание и проверки и сообщать ссылку. Пустой PR GitHub не поддерживает: до первого коммита фиксировать это как незавершённый шаг и открыть PR сразу, как появится push. Если PR создать не удалось, явно сообщить блокер; опубликованная ветка без PR не считается завершённой. Наличие PR не разрешает автоматический merge и не отменяет проверки.

## Локальный вход

```bash
uv sync --locked --extra dev --extra media --extra postgres --extra youtube
uv run python -m ytvideos --help
uv run python -m unittest discover -s tests -p 'test_*.py'
```

[Task contract](operations/task-contract.md) содержит копируемые команды и точную форму outputs/receipts. Справка CLI — источник точного синтаксиса. Агентский вход `start` объединяет создание run, план, диагностику и подготовку reading packet; низкоуровневый `create` сохраняет программную совместимость. `status`, `plan`, `next`, `context`, `complete`, `approve`, `resume`, `cancel`, `doctor` и `import-legacy` обслуживают сохранённое состояние. Локальный `approve --run ...` записывает реальное явное решение владельца по [контракту](operations/task-contract.md#approval-и-продолжение), без ключей/hooks. `approve --event FILE` сохраняет signed-only интеграцию для host с публичным ключом; согласие пользователя не выдумывать.

SQLite использовать для изолированных tests/local runs. Для production PostgreSQL integration проверить транзакции/конкуренцию и actual driver; skipped database tests не считать PASS реального Postgres. Missing native fonts/provider credentials не подменять фиктивным live output.

## Что проверять

Начинать с дешёвого offline gate, затем проверять изменённое поведение:

| Изменение | Адресная локальная проверка |
|---|---|
| Docs, ссылки, skill/catalog | `python scripts/check_repository.py` |
| Checker/navigation | `uv run --no-sync python -m unittest discover -s tests -p 'test_repository_check.py'` |
| Task documents, profiles, recipes | `uv run --no-sync python -m unittest discover -s tests -p 'test_context.py'` |
| State, approvals, releases | Соответствующий `tests/test_*.py`, затем общий core suite из setup |
| Media/YouTube helper | `unittest discover -s automation/<нужная suite> -p 'test_*.py'` в locked environment |

CI остаётся общим gate с реальным PostgreSQL и всеми automation suites. Адресная локальная проверка сокращает обратную связь, но не заменяет CI. `test_app_server`/`test_image_host` в CI намеренно выполняются также до установки media packages: это проверка независимости native protocol от FFmpeg, а не основание удалить общий regression run.

Обязательные регрессии: новый сюжет без bundle; generic profiles; ровно два бизнес-gates; packaging не ждёт MP4; stale artifact/approval/worker; unknown upload; повтор user event; lease conflict; частичная invalidation; scene-pool backpressure/fairness; cancel с in-flight operation; complete без обязательного evidence; wrong channel; schedule в прошлом; Shorts thumbnail до обработки.

Для сложных skills — свежая GPT-6 Luna с обычным заданием без ожидаемого маршрута в prompt. Проверять сохранённый output и реальные вызовы/trace, не только самоотчёт. Отдельная сценарная проба должна пройти исследование, самостоятельный выбор темы, полный текст и остановку на script gate. Не отправлять реальные публикации и не тратить production budget ради тестов MR.

Измерять active time отдельно от user waiting, tokens/tools/cost, retries, долю reuse/resume, реальные interventions и ошибки wrong-skill/wrong-channel/stale-input. Цели ускорения устанавливать после baseline; число сессий и размер prompt сами не доказывают выигрыш.

## Skills и документация

Skill и навык — один procedural слой. `AGENTS.md` маршрутизирует запрос, skill объясняет текущую задачу, общий standard владеет повторяемым требованием, профиль хранит отличия канала, code/schema проверяет переходы и артефакты. Тексты содержат действующие правила; причины пересмотра и отменённые варианты доступны в Git и исследовательских evidence.

`.agent/skill-catalog.json` содержит canonical names/paths/stages/intents; description должен точно совпадать с frontmatter skill. Markdown-каталог генерируется, вручную его не редактировать:

```bash
python scripts/check_repository.py --render-catalog > .agent/skill-catalog.md
python scripts/check_repository.py
```

Checker проверяет current entrypoints, PROFILE.md и явные context references, относительные ссылки/anchors и catalog drift. Архивные журналы не становятся действующими инструкциями. В source-only snapshot можно передать `--known-paths FILE` с проверенным списком remote tracked paths; для anchors всё равно требуется содержимое документа. Skill описывает триггер, необходимые входы, короткую процедуру и результат. Содержание стандарта не копировать в каждый skill. Python helpers находятся в `automation/helpers/`, а не внутри инструкций.

Новый channel recipe объявлять через `context_references` по [task contract](operations/task-contract.md#требования-в-контексте), проверяя правильный stage/format/purpose и отсутствие лишних документов. Не дублировать selector внутри worker. Проверять missing-input и stale-context cases. Независимый reviewer получает артефакт/задачу без диагноза автора. Новая модельная сессия не должна зависеть от предыдущего рассказа координатора.

## Secrets и артефакты

Ключи/OAuth tokens/private approval key и media не входят в Git. Public verifier key нужен только для необязательного signed-only host, не для обычного локального approval. Не печатать credentials при doctor/errors. Большие cache/output складывать в runtime workspace, не source checkout. Реальный файл, подвергнутый QA, связывать с хешем и provenance.

## Проверка полноты исходного запроса

Перед завершением архитектурного изменения сверить [матрицу готовности](operations/readiness.md). Отдельно перечислить выполненные software tests, live evidence и ещё не подключённые runtime-компоненты. CI сохраняет test logs и точный отфильтрованный source snapshot для воспроизведения; это не backup production media. Повтор request/event delivery проверять с разными PostgreSQL connections, а не только последовательными SQLite вызовами.
