# Эксперименты с обложками

Открывать при подготовке A/B, фиксации результата или выборе следующего теста. Создание концептов и QA изображения — [thumbnails](../standards/thumbnails.md); полномочия, provider capabilities и фактическая настройка — [release](../standards/release.md#end-screen-и-ab). План, подтверждённый запуск и наблюдённый результат — отдельные состояния.

Разделы: [план и наблюдение](#план-сравнения-и-ручная-фиксация), [интерпретация](#интерпретация), [следующий тест](#следующий-тест-и-аудитория).

## План сравнения и ручная фиксация

До запуска записать проверяемую гипотезу: что меняется, почему ожидается разница, какой результат поддержит объяснение и какие альтернативные причины останутся. Указать задачу сравнения: выбор концепции целиком или доработка отдельного компонента; при наличии каталога связать варианты с `format_id` и применённым приёмом. Эти сведения хранить в supporting note вместе с исходными IDs и результатом. Поле `ReleaseSpec.ab_variants` принимает 2–3 варианта title + thumbnail hash; это та же строгая схема, что у packaging output. План исследования хранится отдельно и не расширяет её. Доступность и разрешённый режим проверять в актуальной capability. При смене пары целиком результат относится ко всей паре.

Режимы сравнения записывать точно:

- `thumbnail_only` — title фиксирован, меняется изображение;
- `title_only` — thumbnail фиксирован, меняется title;
- `title_thumbnail_pair` — меняются title и изображение как пакет.

Одновременная рандомизированная раздача вариантов (native A/B, если доступен) меньше смешивает эффект с временем/аудиторией, чем последовательная замена. Последовательное сравнение разных дат — наблюдение с меняющимися источниками трафика, охватом и составом зрителей, не причинный A/B. Для проверки компонента удерживать другие значимые условия неизменными. Не объяснять победу одним элементом, если одновременно менялись несколько.

[Образец plan/observation](../examples/thumbnail-experiment.json) показывает форму двух отдельных supporting artifacts; это не валидируемая runtime schema.

Заменить шаблонные значения наблюдениями; не оставлять текст-пример как факт. Для запуска плана нужны точные title, существующие source asset refs и hashes фактических исходных файлов. В этой ручной заметке до появления файла hash остаётся `null`; в strict ReleaseSpec отсутствующее поле опускается. `actual_displayed_variants` связывает provider labels (например A/B) с исходными `source_asset_sha256` и exact title, которые действительно показывались. Не связывать их с hash перекодированного/скачанного preview. `run_id`, `video_id` и release binding заполнять когда известны; отсутствие метрики — `null`, а не оценка. В observation добавить точные даты/окно, timezone, единицы (процент или доля), источник трафика и доступный denominator каждого показателя; `evidence` содержит concrete receipt/Studio read-back/source reference, method и observed values. Статус отражает наблюдение (`planned`, `running`, `completed`, `stopped` или `unverified`), не предполагаемый будущий исход.

Хранить заметки как supporting artifacts через процедуру [task contract](task-contract.md#источники-и-обложки). Сохранение не означает, что приложение проверило поля или включило заметку в task input. Все попытки, включая stopped, проигравшие, Performed Same и Inconclusive, сохранять; не перезаписывать план прошедшим тестом. Пока A/B ожидает запуска или выполняется, обеспечить доступность исходных bytes всех нужных вариантов; управлять retention и очисткой по [storage policy](../standards/storage.md). После очистки сохранить записи, IDs, названия, hashes и evidence; журнал результата не требует вечного хранения медиа.

## Интерпретация

Native YouTube A/B оценивает варианты по доле времени просмотра (watch time share), не по CTR; возможны `Winner`, `Performed Same`, `Inconclusive`. Записывать точный provider verdict. Winner означает преимущество по критерию этого теста; Performed Same не доказывает точное равенство; Inconclusive — отсутствие уверенного вывода, не нулевой эффект.

CTR брать только из соответствующего источника и когорты зарегистрированных показов. Записывать окно, источник трафика, знаменатель и доступные сегменты. Не подставлять общий CTR ролика в поля отдельных вариантов; не восстанавливать CTR из views или watch-time share. Публичные просмотры чужого ролика не раскрывают CTR.

Для оценки соответствия обещания смотреть также соответствующее время просмотра/удовлетворённость, если доступны такие данные. Не выводить рекомендательный эффект по одной метрике: публичной фиксированной формулы ранжирования нет. Любое обобщение на другие темы/аудитории — новая гипотеза, особенно при последовательном сравнении.

## Следующий тест и аудитория

Дождаться завершённого provider verdict; промежуточные проценты сами по себе не определяют победителя. `Performed Same` и `Inconclusive` также завершают тест: не ждать обязательного `Winner` бесконечно и не переименовывать редакторский выбор в измеренное преимущество. Явно остановленный тест сохранять как stopped с причиной.

После выбора концепции сохранить текущую сильную пару как контроль следующего сравнения и проверить конкретное изменение: надпись, предмет, окружение, выражение или свет. При `Winner` контроль берётся из подтверждённого результата; иначе назвать основание рабочего выбора. Для вывода об одном компоненте удерживать остальные значимые условия; новая смысловая концепция проверяет всю пару. Каждый запуск получает отдельный plan/observation и ссылку на предыдущий результат.

Проверять доступные источники показов, окна и сегменты: ранние показы могут чаще приходиться на знакомых с каналом зрителей, поздние — на новых ([YouTube A/B FAQ](https://support.google.com/youtube/answer/16391400?hl=en)). При наблюдаемом изменении состава аудитории сформулировать новую причину интереса для незнакомого зрителя и сравнить вариант с текущим. Native test не объявлять таргетированным на сегмент без такой capability; данные общего состава аудитории — контекст гипотезы. Снижение общего CTR при расширении показов само по себе не доказывает дефект картинки ([CTR FAQ](https://support.google.com/youtube/answer/7628154?hl=en)).

Рассказ автора о волнах охвата использовать как рабочую модель для поиска гипотез; это не гарантированная последовательность раздачи всем зрителям. Две недели из примера не задают автоматическую замену. При недостатке данных сохранить вопрос для следующего наблюдения. Повторный запуск требует доступного provider, разрешённого scope, бюджета и read-back по текущему release flow; pending запись сама его не выполняет. Замена title/thumbnail во время native test останавливает его: сначала проверить действующий эксперимент и сохранить фактический исход, затем готовить новый.
